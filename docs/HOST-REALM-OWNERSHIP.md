# Host persistent account realm integration

Source-only extension of the consumer prototype. Public runtime activation
guards remain in place. Nothing here creates accounts, entitlements, production
resources, a new authority route or a new service. The authority envelope in
`REALM-CONSUMER-PROTOTYPE.md` remains unchanged.

## Persistent ownership boundary

`HostRealmOwnership` binds the validated tuple `(issuer, raw subject)` to its
public DTO and exact internal storage key in `host_realm_bindings`, with a
version marker in `host_realm_metadata`. Legacy keys stay byte-for-byte bare
IDs; fresh keys are the leading-space reversible tuple defined in the shared
contract. Existing legacy IDs equal to fresh public DTO hashes stay legacy.
The virtual `owner` row preserves Host's existing shared infrastructure tenant;
only the legacy issuer plus the existing actual ID/role/MFA owner policy may
resolve that group through website authentication.

Binding rows cannot be updated, deleted or replaced with a different tuple.
Each of the nine existing tenant tables has insert and ownership-update guards:
nodes, projects, deployments, project_replicas, domains, credentials,
usage_events, app_builds and activity. New rows require an existing binding.
Updating ownership or replacing an existing row ID with another tenant is
refused, including SQLite `INSERT OR REPLACE`. Normal updates within the
existing tenant remain possible. The registry checks the exact expected table
and trigger definitions on each resolution; incomplete/tampered metadata fails
closed for both realms. Ordinary application code cannot select a caller-supplied
issuer/key or grant ownership from email, headers or a public DTO.

Protected website requests first revalidate the opaque cookie at the fixed
private authority, then resolve the persistent key. Concurrent binding writes
use one atomic libSQL batch without holding a local SQLite writer transaction
across JavaScript yields. Native/local Host account attachment remains
legacy-only and validates the legacy subject domain. Fresh website identities
never enter its historical same-email attachment or local session minting path.

Hub preferences/audit and Host session/cache identities use the typed key or
separate realm prefix. Legacy preference/audit hashes are unchanged. The Hub
public session DTO carries its server-derived `identityKey`; this field is for
cache invalidation, never authorization. CMS publishing remains legacy-owner
only with the exact configured identity, authoritative role and actual MFA.

## Explicit migration and rollback gates

`initialize()` is an explicit maintenance operation, never a login side effect.
It requires all nine existing resource tables and does not invent or rebuild
their schemas. In one transaction it labels all existing tenant IDs and stored
native account IDs as legacy, preserves every resource/account field, creates
the new integration tables/triggers and verifies them before committing.
Existing leading-space/internal-domain keys or `__unassigned__` resource rows
are refused atomically. They must be resolved using actual ownership evidence;
they are never silently adopted as fresh or owner data. Re-running a complete
valid migration is idempotent. A partial schema is refused rather than repaired
by guessing.

With no registry, legacy-only resolution keeps its old exact keys and makes no
migration writes; fresh access is refused. After migration, every new validated
legacy identity is registered before its first resource write. A later raw
legacy ID equal to a fresh public hash therefore still cannot acquire a fresh
tenant. All accepted legacy/native inputs must continue to reject whitespace
and control keys; do not trim a private key into a different identity.

Before runtime activation, independently review the actual deployed Host
source/schema, stop every writer, capture consistent reversible backups,
stage `initialize()` on a copy, verify all old fields/resources and bindings,
exercise the deployed backup/restore, and test the real owner plus normal A/B
accounts. Keep the original account authority/client contracts until their
compatibility checks pass. No CLI entry point here operates on production.
The current runtime prototype guard remains mandatory.

Do not run `drizzle-kit push` against a migrated registry database: these
integration tables/triggers are deliberately outside the existing generated
application schema. Any future schema migration must explicitly preserve and
verify them. Losing a guard fails authentication closed; losing tuple metadata
must be recovered from a verified backup, never regenerated by reclassifying
existing internal keys. Rolling back to old consumers is safe only before
fresh writes, or by restoring the coordinated pre-activation snapshot while
all writers remain stopped. Old code cannot safely interpret fresh internal
keys or enforce the new tuple boundary.

## Evidence and limits

Tests use actual local SQLite/libSQL files, generated current Drizzle schemas
and actual Host procedures. They cover a legacy bare ID equal to a fresh
public DTO, fresh A/B with the same email, simultaneous binding, exact tuple
persistence across two real processes, all nine tenant tables, future legacy
bindings, ownership UPDATE/REPLACE refusal, binding replacement/deletion
refusal, missing-trigger failure and atomic refusal of unlabelled internal
keys. Real nodes/projects/settings procedures verify own resource lists,
cross-tenant node-token rotation/project read/node assignment denials, and
separate provider hints without returning or using provider secrets.

Separate consumer tests cover owner/role/header forgery, expired/revoked
authority sessions, ambiguous cookies, CSRF, preserved legacy login and refusal
to attach a fresh same-email account. The full Hub/CMS suite covers native CMS
Box integration, owner-only operations, unchanged legacy hashes and the public
DTO collision in preference and UI cache identities.

These fixtures do not establish actual VPS/device enrollment, subscriptions,
provider billing or mail delivery. Host currently has no reviewed subscription
adapter; this extension creates no paid rights. Fresh Bridge/default native
client login and all-client migration remain separate acceptance gates. RedX
engine/BoxQL/files code and deployed native data are untouched by this Host
worktree. No push, deployment, production API request or credential was used.

Local validation on 2026-11-03 with pinned Bun 1.3.14: all 48 API tests, all
13 mounted-auth/embed tests, all 74 Hub/CMS Node tests and both Host TypeScript
checks passed. The process-restart and actual procedure fixtures are included
in those counts. No hosted CI, Linux staging migration or live user acceptance
is claimed by these Windows-local results.
