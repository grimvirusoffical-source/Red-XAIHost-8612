# Account compatibility checkpoint

The Hub is a presentation and routing adapter for the existing private account authority on port 4200. It does not issue sessions, change verification state, skip required MFA, edit account storage or substitute the separate Accounts repository.

Registration remains delegated byte-for-byte to `/signup`, `/activate`, `/tos` and the original backend routes. Its visible fields are first/middle/last name, username, birth date, email plus confirmation and password plus confirmation. Availability checks, validators and accepted Terms remain the existing implementation. Public frontend statements are not proof of server validation or data-retention behavior.

Password sign-in posts `{login,password}` to `/api/accounts/login`. Responses with `next: "2fa"` or `next: "2fa_setup"` and a flow token are incomplete authentication. Challenge calls preserve `/api/accounts/login/call`, `/login/2fa`, enrollment `/2fa/totp/start`, `/confirm`, the corresponding phone routes and `x-redx-flow`. Flow tokens remain in memory and are cleared on Back, completion, expiry and disposal. Discarded flows cannot process late responses or expire a newer flow. A completion still requires canonical website-session verification. A pending token, challenge, error or unresolved next step cannot finish the Hub's MFA check.

The existing legacy challenge UI restarts sign-in for HTTP 401 or `error: "tries"`; the new Hub preserves that behavior. Email-verification routing requires a specific activation denial. An outage or generic account-deactivation error remains an error. Quick Login prefixes and developer-client protocols are unchanged.

The running legacy revision is `bcc6c62a2f119bd833ba083c12a3799ca622b980`; matching source remains missing. The user has authorized preparing a compatible replacement while existing production authentication stays active. Public calls establish transport compatibility, not the account storage or migration schema. Optional normal-user MFA requires the authority to issue a completed password session when policy permits. Existing enrolled/owner MFA must remain enforced. Owner ID, role and a completed MFA method do not establish recent step-up authentication.

Before a replacement can serve existing identities it needs a consistent, restorable original-account export and verified mappings for immutable IDs, password verifiers/encryption, cookies/sessions, flow/activation tokens, MFA secrets, accepted Terms, registration validation and existing external API/Quick Login contracts. Resend, verified-email administration, revocation and deletion are not established merely by routing the same endpoint names. No production migration or direct flag edits are part of this patch.

`node --test account-flow.test.mjs frontend.test.mjs` passed 19 tests, including stale responses, expired-token reset, incorrect code/outages, unresolved MFA and activation classification. These fixtures do not prove production delivery, optional MFA or live two-account isolation.

The separate future `scripts/primary-account-activation.cjs` adapter accepts only the reviewed Hub-completion asset (`f531bead2e2fd314ea1fc5a05e19ae248695d603d57bc1a985eb04018832c327`). It changes only the activation success expression in `vN`: an explicit HTTP 200 response with `signInRequired: true` and no flow token returns to `/signin`. It creates no session and declares no completed MFA. Existing enrollment responses and errors keep their original behavior. Signup fields, validators, Terms and surrounding bytes remain unchanged. The staged output is `d3ed808add659cda14d821e8d2ad178fe852132e3cf125c14430ac64436e7877`; four additional fixture tests and the full asset byte comparison pass. It is not deployed and must not be applied until the compatible account authority's migration and browser/client contracts pass. It does not repair the current backend's forced-MFA or email-delivery policy.
