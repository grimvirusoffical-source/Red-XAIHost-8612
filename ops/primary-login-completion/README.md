The recovered primary website sign-in component ignores direct HTTP 200 success
when the account service does not request a second factor. It handles only
`next: "2fa"` and `next: "2fa_setup"`, so a password-only success can leave the
sign-in screen visible. This package adds the component's existing completion
hook to that missing success path.

The fixtures are the publicly served legacy website bundle and its exact patched
result. The matching editable frontend source and legacy backend source were not
recovered. The current Host application in this repository is a different
implementation; this package does not modify its runtime source or build.

This is a frontend completion fix only. It does not fix backend credential or
activation errors, change email verification or MFA policy, add an enrollment
skip, or prove that an affected user's account can sign in. **A live affected-user
sign-in test remains unverified.**

The patch changes only `pN`. It initializes the existing `tg()` hook, preserves
both second-factor transitions, and calls completion after HTTP 200 only when
`next` is absent or empty, `token`, `challenge` and `error` are absent, and
`pending` is absent or an empty array. Other unresolved responses show a visible
error. The unchanged hook updates the safe return URL and invalidates `['me']`;
the gate still waits for the authoritative server identity response. The patch
does not create a signed-in identity, authentication cookie or verification claim.

Use Node.js 20 or newer. There are no dependencies to install. From this directory:

```sh
node --test login-regression.test.cjs
node --check patch-login.cjs
node --check login-regression.test.cjs
node --check fixtures/index-customers-console-aeeeebb35bec.js
node --check fixtures/index-customers-console-81b28895ccc8.js
```

All 17 VM tests pass. They run the actual recovered component and existing
completion hook, reproduce the original stall, verify authoritative `/me`
false/true outcomes, preserve MFA/enrollment/error responses, reject unknown
pending responses, and compare the shipped patched fixture with generated bytes.

To generate a separate candidate file:

```sh
node patch-login.cjs fixtures/index-customers-console-aeeeebb35bec.js /tmp/primary-login-candidate.js
node --check /tmp/primary-login-candidate.js
```

The patcher reads the original and exclusively creates a new output. It rejects
changed input, duplicate matches, repeat application, identical input/output
paths and an existing output. It does not deploy files or change HTML, services,
account records or configuration. A separately authorized rollout must verify
the exact live-input digest, preserve the asset and referring HTML for rollback,
and validate the candidate before changing a versioned asset reference.
